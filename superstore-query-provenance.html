GrainOffice Supplies moves the most units (45) but earns the least revenue and has the thinnest margin (21.5%). Technology sells only 9 units yet posts the best margin (27.8%) — volume and profitability rank differently here, so "performing well" needs a metric named, not assumed.

SQL executed · category_performance
SELECT  products.category,
        SUM(orders.sales)                            AS total_sales,
        SUM(orders.profit)                           AS total_profit,
        SUM(orders.profit) / NULLIF(SUM(orders.sales), 0) * 100 AS profit_margin_pct,
        SUM(orders.quantity)                        AS units_sold
FROM    orders JOIN products ON orders.product_id = products.product_id
GROUP BY products.category
ORDER BY total_sales DESC;

Question 02 · direct match, grain matters

"How many orders did we get?"

Matched
order_count
Adaptation
none
Grain
distinct orders, not line items
Basis
25 lines across 13 orders
Stage 2 · matchthe trap this dataset sets

orders is stored at line-item grain — 25 rows for 13 real orders, because a multi-product order gets one row per product. A plain COUNT(*) would answer "how many order lines," not "how many orders."

Stage 5 · resultsingle scalar
13 COUNT(DISTINCT order_id) — the only correct way to count orders on this table. COUNT(*) here would have reported 25.
GrainThe largest single order in this extract spans 7 line items. Any metric that touches order-level fields (order date, ship date, ship mode, customer) has to deduplicate to one row per order first, or it double- and triple-counts. order_count and orders_by_ship_mode both do this correctly by construction, not by convention.
SQL executed · order_count
SELECT  COUNT(DISTINCT order_id) AS order_count
FROM    orders;

SQL executed · region_profitability
SELECT  customers.region,
        SUM(orders.sales)   AS total_sales,
        SUM(orders.profit)  AS total_profit
FROM    orders JOIN customers ON orders.customer_id = customers.customer_id
GROUP BY customers.region
ORDER BY total_profit ASC;

        SUM(orders.sales)   AS total_sales,
        SUM(orders.profit)  AS total_profit
FROM    orders JOIN customers ON orders.customer_id = customers.customer_id

ORDER BY total_profit DESC

AnswerEvery discounted band except 15% shows negative aggregate margin, and margin falls sharply as the discount deepens: 0% → +29.3%, 20% → −10.8%, 60–80% → −70% to −170%. Margin crosses into loss somewhere between 15% and 20% off.
What this does not tell youNo historical line item sits between 21% and 59% discount — the data jumps straight from 20% to 60%. A 25% blanket promo cannot be interpolated from this table with any confidence: doing so would assume volume and customer behavior stay fixed under a new price point, an assumption this dataset contains zero evidence for either way. This query can describe what discounting has looked like historically; it cannot forecast a scenario the data has never seen.
SQL executed · discount_level_margin_relationship
SELECT  discount,
        COUNT(*)                                AS n_line_items,
        SUM(sales)                              AS total_sales,
        SUM(profit)                             AS total_profit,
        SUM(profit) / NULLIF(SUM(sales), 0) * 100 AS profit_margin_pct
FROM    orders
GROUP BY discount
ORDER BY discount ASC;
